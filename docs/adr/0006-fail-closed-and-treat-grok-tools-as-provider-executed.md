# Fail closed and treat Grok tools as provider-executed

Every built-in launch path passes `--permission-mode` explicitly so ambient user or repository configuration cannot silently substitute a more permissive mode, but the safe implicit value depends on the transport. Headless `grokExec` defaults to `dontAsk` because its child is spawned without an interactive input channel, while ACP defaults to `default` because its JSON-RPC channel can answer permission requests. A custom `GrokBuildLanguageModel` `clientFactory` owns its arguments and must preserve this invariant itself.

Dangerous permission bypass uses call-level nullish precedence over provider settings, so an explicit per-call `dangerouslySkipPermissions: false` disables only a provider-level dangerous bypass. It does not reset an independently configured `permissionMode` or `alwaysApprove`; those settings retain their own call-level then provider-level precedence. The one resolved bypass value determines both ACP permission handling and built-in CLI arguments. When bypass is true it supersedes ordinary permission-mode and approval flags rather than passing contradictory arguments.

An unhandled ACP permission request fails closed, and only an explicit approval or bypass setting may select an allow outcome automatically. Every permission result, including a custom `session/request_permission` handler result, must structurally contain a selected or cancelled outcome and is validated against the options advertised by the agent before it is returned. Undefined or malformed results produce a typed `AcpPermissionError` response rather than an incidental JavaScript exception. Session cancellation takes precedence over queued or running approval logic and produces the ACP `cancelled` outcome rather than allowing work for a cancelled session. Grok-native and MCP tools are reported as provider-executed and must not be executed again by the application; unsupported AI SDK tool registration produces a warning rather than pretending that a result channel exists.

A custom client factory receives resolved process settings such as permission handling, environment, and timeouts, but no provider-generated `args` by default. This preserves wrapper ownership of the command line, and client-side ACP permission handling alone does not place the child CLI into plan mode. A real-CLI factory can set `validateCli: true` to receive the complete generated Grok arguments; default construction and the internal pooled provider enable that path automatically.
