# Bound and explicitly own pooled ACP clients

`grokAgent` pools clients by effective process and callback configuration after defaults and environment values are resolved, excluding model and effort because those belong to sessions. Callback identities participate in the key, while filesystem read/write handlers are keyed individually so equivalent settings survive schema-created wrapper objects without accidentally sharing clients that have different behavior.

The pool defaults to eight clients, replaces stale clients, evicts the least-recently-used idle client, and rejects a new identity with `POOL_CAPACITY_EXCEEDED` when every client is active. An idempotent generation lease makes a client non-idle from acquisition through preparation and prompting—including gaps between ACP requests—so capacity pressure cannot dispose a live generation. Inbound permission, filesystem, and custom request handlers also make the client non-idle until their per-session queue drains, preventing eviction during a partially completed side effect such as a file write. Invalid `maxClients` remains a constructor `TypeError` as the established configuration-validation contract.

An unusable client that is still collecting terminal diagnostics is removed from active lookup and replaced without being disposed. It enters a retired set until its one-shot terminal-settlement signal resolves, then is disposed. Retired clients do not count against `maxClients`, so the pool may temporarily exceed its configured capacity during the bounded diagnostic window; this preserves complete exit and stderr diagnostics for in-flight requests without making a damaged client available to new work.

Persistent clients deliberately have no idle timer or automatic shutdown hook, so consumers must call `close()` or async disposal, including when using the exported singleton. Detached eviction disposals are tracked with rejection absorbed, and `close()` awaits current clients, retired clients, and pending disposal work before it resolves. Disposal resolves any provisional terminal-stdin failure before enqueueing cancellation writes, so a broken write cannot strand the serialized write queue or prevent the bounded `SIGTERM`/`SIGKILL` shutdown path from completing.

Update and extension callbacks are observational with respect to the shared transport outcome, not completion latency: an exception from one consumer callback cannot fail a successful prompt, the shared client, or another session, but ordered callback delivery may delay exposing the owning request's result. Request timeout, abort, disposal, and terminal-failure settlement remain active during that delay, so a callback cannot make request settlement unbounded and a later callback-barrier completion cannot overwrite an earlier terminal outcome. The AI SDK adapter's prompt-update handler deliberately translates its own normalization or emission failures into an abort of only the owning prompt and reports the original error through that generation's stream; that adapter control flow is distinct from propagation of a consumer-hook exception.
