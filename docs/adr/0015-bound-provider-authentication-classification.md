# Bound provider authentication classification

Canonical ACP authentication-required error `-32000` maps to the provider authentication surface for every request method, while legacy `-32603` credential diagnostics are accepted only for anchored known messages from provider-owned initialization, authentication, and session-setup methods. Headless authentication inference is likewise restricted to known diagnostics from completed headless or process-exit failures, excluding low-severity API-key mentions and unrelated failure classes. Agent diagnostics are ANSI-safe, control-safe, selected and credential-redacted per line, and bounded before they reach public errors; each diagnostic is classified independently so adjacent output cannot hide an authentication failure. Structured diagnostic data is redacted and has a hard 8 KiB serialized UTF-8 limit, with depth, width, node, and string bounds. Request-level JSON-RPC, authentication, and timeout errors do not attach the process-wide stderr buffer because concurrent sessions cannot correlate it reliably. Initialization failures may retain a sanitized stderr tail because initialization is exclusive, while actual process and transport failures continue to retain one.

`session/new` and `session/load` permit at most one authentication retry without replaying prompts or configuration changes. A retry occurs only when the configured method is advertised. A configured method absent from a non-empty advertised list produces `AUTH_METHOD_NOT_AVAILABLE` with the available methods and the original request as its cause; when the agent advertises no methods, the original request failure is preserved. Authentication and retried-request failures are represented by fresh errors rather than mutating shared transport errors or caller-owned abort reasons. The top-level retry error remains authoritative while an aggregate cause retains the original initial and retry errors. Direct `AcpClient.loadSession()` callers continue to receive the original `AcpJsonRpcError` for wire authentication failures, while the AI SDK adapter maps it to `LoadAPIKeyError` with the original sanitized error as `cause`.

The low-level client reports transport diagnostics without provider configuration advice. The AI SDK adapter appends remediation once and tailors it to the effective mode: cached-token failures recommend `grok login`, API-key failures recommend verifying or replacing `apiKey` or `XAI_API_KEY` without recommending login, and custom or unavailable methods distinguish advertised ACP methods from the provider-only `api_key` mode.
