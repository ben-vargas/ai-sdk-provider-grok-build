# Preserve transport-native session semantics

Client-initiated ACP load, prompt, and `session/set_config_option` operations are serialized for the same session while different sessions may issue operations concurrently. A queued caller observes abort immediately, but its internal queue placeholder remains until its turn so later operations cannot overtake it; loading or configuring a session therefore cannot race a live prompt on that session.

Inbound ACP messages retain ordered parsing, but agent-to-client permission, filesystem, and custom requests are dispatched to FIFO queues keyed by `params.sessionId`. Before an agent request runs, it waits for notification callbacks already queued for that session, so a permission handler observes the tool update that introduced its request. Requests for one session cannot overtake each other, while a pending callback or handler does not block responses, notifications, or handlers for another session. Missing, empty, or malformed session identifiers use one tracked fallback queue so they remain ordered and keep the client non-idle. Process-exit draining does not await agent-handler queues, because a hung consumer handler must not delay reporting that the agent process crashed.

Stdout parsing and JSON-RPC correlation do not await consumer notification handlers. Each notification snapshots the handlers applicable when it is parsed and enters the ordered callback queue for its session or the sessionless stream. A response outcome is normally exposed only after its applicable callback barrier completes: session requests wait for their session, `initialize` and `authenticate` wait for the sessionless stream, and `session/new` waits for both the sessionless stream and the returned session ID. The pending request, deadline, abort listener, disposal path, and terminal-failure path remain active while the barrier is pending, so any of those outcomes may settle first and a process failure may reject a response that was already received. This preserves callback-before-completion ordering without letting callback latency block protocol parsing, unrelated sessions, or bounded failure settlement.

Per-prompt update handlers are represented by active registrations. Prompt cleanup deactivates and removes its registration, abort deactivates it immediately, and a captured callback that has not started by then is skipped. A callback already running remains observational and is not forcibly interrupted.

Permission cancellation state is registered as soon as `session/request_permission` is received, before the request enters its per-session queue. Queued and running permission handlers race the same cancellation signal, so cancelling a session returns ACP's `cancelled` outcome without invoking a not-yet-started approval callback or selecting an automatic allow option; later permission requests receive independent cancellation state. This preserves per-session FIFO and cross-session concurrency without coupling permission work to the client-initiated session-operation queue.

Extension observation begins before initialization and session creation so live notifications from those operations are not lost. Session-tagged notifications are buffered until the new or loaded session ID is known, then only untagged or matching-session events are retained; notifications marked `_meta.isReplay` remain quarantined rather than becoming output from the next generation.

ACP supports explicit session loading but does not emulate continue or fork operations it cannot perform; headless mode instead maps and validates Grok's native resume, continue, fork, and named-session controls. Session and request identifiers remain local to each generation and are reported in its finish metadata.
